# Benchmarks

Compares caseparser with other libraries that convert strings and object keys between cases: speed, memory, bundle size, features and security.

## Running

One command, from the repository root, builds caseparser, installs the libraries compared (with the versions in the lockfile) and runs everything (~15 minutes):

```sh
pnpm install
pnpm benchmark
```

It writes every result to [`results/`](./results). For stable speed results, close other apps and keep the computer plugged in.

The steps can also run one at a time, in this folder (after `pnpm run build` in the root and `pnpm install` here):

```sh
pnpm test         # checks every library and writes the features, security, edge cases and correctness results
pnpm bench        # speed on Node.js (~6 minutes); `pnpm bench:bun` and `pnpm bench:deno` on Bun and Deno
pnpm memory       # memory, on Node.js (~8 minutes)
pnpm size         # bundle size
```

`pnpm test` fails when a result in `results/` changes (run `pnpm test -u` to update them); `pnpm benchmark` updates them.

## Method

### Libraries

Each file in [`libraries/`](./libraries) calls one library, converting deeply with its documented option when it has one:

- [`change-case`](./libraries/change-case.ts): `change-case/keys` is passed the depth `Infinity` (without it, only the first level is converted).
- [`camelcase-keys`](./libraries/camelcase-keys.ts) is passed `{ deep: true }`.
- `snakecase-keys`, `humps` and `es-toolkit` convert deeply by default.
- Cases without their own function use the library's documented option: the `delimiter` of change-case and snakecase-keys, the `separator` of humps.
- caseparser keeps the case of each word in dot.case and path/case by default, so it's called with `{ transform: 'lowercase' }` in those two.
- **caseparser** is measured twice: the current source (`caseparser`, built from `src`) and the published version (`caseparser@5.1.0`).

### Data

Inputs and expected outputs ([`common/fixtures.ts`](./common/fixtures.ts)) are written by hand, not generated by any of the libraries. The keys are plain words, with no digits or acronyms, which every library can convert, so speed isn't decided by how a library handles edge cases. Each key is a list of words, joined in each case by `joinCase`, which is checked against the hand-written snake_case and camelCase data.

snake_case keys are converted to camelCase and PascalCase, and camelCase keys to the other cases, because humps and snakecase-keys only convert from camelCase to the cases with a separator.

### Speed

- **Correctness first:** before measuring, the output of each library is compared with the expected one, including nested objects and prototypes. A library that returns anything else is not measured in that scenario, and is marked ⚠️. [`correctness.md`](./results/correctness.md) shows which libraries passed each scenario.
- **Measurement** ([`speed/speed.bench.ts`](./speed/speed.bench.ts)): `vitest bench` (tinybench), one library at a time, with 0.2s of warmup and 0.5s of measurement. The result of every iteration is kept, so the engine can't skip unused work.
- **3 rounds:** every scenario is measured 3 times, and the order of the libraries rotates between rounds, so no library is always measured first or last. The time shown is the mean of the medians of the 3 rounds, and each round is in the tables and in the JSON.
- **Ties:** the fastest library is in bold, and so is any library whose medians in the 3 rounds overlap with the fastest's. Results change between rounds (up to ~20% in the scenarios with unique keys, which create a lot of garbage), so a smaller difference is not a win.

| Scenario | What it measures |
| --- | --- |
| Repeated keys, to each case | A paginated API response with 100 users (2,104 keys, nested objects and arrays of objects), the same object in every iteration. Every user has the same keys, like real API responses. Libraries that reuse work (caseparser converts each distinct key once per call; camelcase-keys keeps a cache between calls) benefit from it, as they would in an app. |
| Unique keys, to each case | Each iteration converts a different object from a pool of 256 objects with 1,000 keys each, and no key repeats in the pool (256,000 keys). The pool is larger than the camelcase-keys cache (up to 2 × 100,000 keys), so no library can reuse work between or within calls. |
| Small object | A flat object with 8 keys, the same object in every iteration. Shows the fixed cost of each call; the cache camelcase-keys keeps between calls lets it skip converting the keys again. |
| 10 strings | Converts 10 strings in different cases (`user_id`, `firstName`, `ACCOUNT_STATUS`, `Display Name`...). |

Bun uses a different engine (JavaScriptCore) than Node.js and Deno (V8), so the ranking can change between runtimes.

### Memory

[`memory/memory.ts`](./memory/memory.ts) measures, on Node.js:

- **Loading the library:** heap used by importing the library's file in `libraries/`.
- **One call:** heap allocated by converting the API response, the small object or one object with 1,000 unique keys, split into the result and the temporary memory (garbage) the call leaves behind. It's the median of 51 calls, each after a garbage collection (`--expose-gc`), with a young generation large enough (`--max-semi-space-size=64`) that none runs during the call; a call during which one runs is discarded. The memory allocated by measuring itself is subtracted.
- **Kept between calls:** heap still used after converting the 256,000 unique keys and dropping the results, like a cache.

Each measurement runs in a new process ([`memory/worker.ts`](./memory/worker.ts)) that imports only the library measured, 3 times, in an order shuffled with a fixed seed. A single measurement can be checked by running the worker alone, as shown in [`memory.md`](./results/memory.md).

### Features and security

[`checks/features.test.ts`](./checks/features.test.ts) runs every library to fill [`features.md`](./results/features.md):

- **Target cases:** the cases each library converts keys to, from its file in `libraries/`. Each one is checked by converting a key.
- **Input keys in any case:** converts `user_id`, `FirstName`, `last-name`, `ACCOUNT_STATUS`, `Display Name`, `Content-Type`, `billing.address` and `emailAddress` in one object.
- **`Date`, `Map` and class values:** whether they still work after converting the object that contains them, and what happens to class instances. Converting their keys or keeping them as they are are both design choices.
- **Option to skip keys:** checked with the documented option (`ignore` in caseparser, `exclude` in camelcase-keys and snakecase-keys, the callback of humps). The libraries marked ❌ have no such option in their documentation or types.
- **Typed keys:** checked by `tsc` in [`checks/types.check.ts`](./checks/types.check.ts), comparing the type each library infers for a converted object with the keys it returns at runtime. The types of humps come from `@types/humps`.
- **Dependencies:** the packages installed with each library, counted recursively from their `package.json`.

[`checks/security.test.ts`](./checks/security.test.ts) converts JSON with a `__proto__` key, as in a request body. `JSON.parse` creates it as a regular key, but a library that assigns it to the result (`result['__proto__'] = value`) replaces the result's prototype, and the result inherits the properties of that value (like `isAdmin: true`). It also converts JSON with a `constructor` key, which hides `Object.prototype.constructor`: a library that checks for plain objects with `value.constructor === Object` skips the object or fails (caseparser 5.1.0 returned `undefined`).

### Edge cases

[`edge-cases.md`](./results/edge-cases.md) shows what each library returns for inputs with acronyms (`XMLHttpRequest`, `userID`), digits (`html5Parser`), mixed or repeated separators (`LAST_login_AT`, `__private_flag`) and symbols (`$ref`). Some have more than one reasonable answer, so there is no expected output: the table only shows the results.

### Regression test

[`checks/regression.test.ts`](./checks/regression.test.ts) checks that the current source returns exactly what the published caseparser@5.1.0 returns, for the 15 `toX` functions (6.0 removed the deprecated `<from>To<To>` functions), 11 combinations of options and ~30,000 generated strings (letters, digits, separators, symbols, non-ASCII letters, and characters like `ς`, `İ`, `ǅ`, `ß` and emoji, whose case changes depend on context or change their length), plus nested objects and `__proto__` keys. It compares the key order and prototype of every object too.

### Bundle size

[`size/size.ts`](./size/size.ts) bundles the camelCase and snake_case key functions of each library with esbuild (minified, tree-shaken, dependencies included) and gzips them.
